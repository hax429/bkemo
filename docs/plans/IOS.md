# bkemo iOS — Native Quick-Capture App (Plan)

**Server:** `https://bk.hax429.me`
**Stack:** SwiftUI (iOS 17+), SwiftData, App Group, REST via `URLSession`
**Last updated:** 2026-07-23
**Replaces:** previous Tauri/WKWebView iOS plan in full — the Tauri iOS pipeline is
retired (see §13). macOS is intentionally out of scope for this plan.

---

## 1. Goal

A native iOS quick-capture client for bkemo. Speed of opening and capturing is the
first priority; everything else is secondary. The app is **not** the full bkemo web
experience on mobile — browsing, organizing, AI, analytics, calendar, and the
markdown editor all remain on `https://bk.hax429.me`.

In scope:

- One-tap capture of a memo or a todo, with inline `#tags`.
- A quick recent-captures list (API-fetched, capped at ~50) so the user can verify
  captures landed and re-capture similar things.
- iOS Share Extension: share from browser / YouTube / chat apps → save link or text
  as a memo (with `LPMetadataProvider` title extraction).
- iOS Home Screen widget (Small + Medium): one-tap "Memo" / "Todo" → open the app
  with composer pre-set and keyboard up.
- Voice input via the iOS system dictation key in v1; plan a richer native speech
  surface (multilingual + raw-audio attachment) for v2.
- Offline-first writes: the composer is always usable, even on cold launch with no
  network and even on a poor/returning connection. List fetch is lazy and never
  blocks capture.
- Biometric (Face ID / Touch ID) unlock on app launch.

Non-goals (explicit cuts, see §14): markdown editor / preview, attachment upload
from the app body, photo share in v1, voice memo as an audio file in v1, search /
calendar / matrix / graph / analytics / AI, multi-account, server URL prompt,
OTA frontend bundle, iPad layout tuning, task notifications, public-share
generation.

### Success criteria

| # | Goal | Success criteria |
|---|------|------------------|
| G1 | Native SwiftUI app launches and connects to `bk.hax429.me` | Sign in → recent list visible on iPhone |
| G2 | Composer is the first interactive surface on cold launch | Composer renders and focuses keyboard within ~400 ms of icon tap, offline |
| G3 | Offline capture | Capture in airplane mode → row appears locally → on reconnect syncs to server within 3 s |
| G4 | Share Extension saves | Share from Safari/YouTube → bkemo → save → memo appears on server (online) or in local queue (offline) |
| G5 | Widget one-tap | Tap "Todo" on the home-screen widget → app opens with Todo selected, keyboard up, cursor ready |
| G6 | Biometric gate | Kill app, reopen → Face ID prompt → cancel → composer not visible |
| G7 | Voice input | Tap system 🎤 on the keyboard → dictated text appears in composer |
| G8 | TestFlight install | Archive + upload via App Store Connect → TestFlight install on the user's iPhone |

## 2. Architecture

### 2.1 Shape

Single Xcode workspace in a new top-level `ios/` directory in the monorepo, with
three targets that share an App Group container:

```
ios/
  bkemo.xcodeproj                 (or .xcworkspace if SPM involved)
  bkemo/                          (app target, iOS 17+)
    App/      entry, RootView
    Capture/  Composer, TypeToggle, PriorityToggle
    List/     RecentList, MemoRow, MemoDetailSheet
    Data/     SwiftData models + REST client + SyncEngine
    Security/ BiometricGate
    Util/     TagParser, URLMetadata
  ShareExtension/                 (iOS share-extension target)
  Widget/                         (iOS WidgetKit extension)
  Shared/                         (Swift PM local package or shared sources)
```

Each target's Info.plist declares the same App Group (`group.me.hax429.bk`) so
SwiftData, the auth token, and the pending-queue all live in one container the
widget and the share extension can read/write.

> Repo placement rationale: keep it out of `app/src-tauri/gen/apple/` (that
> directory is generated by Tauri and will be retired — mixing a hand-written
> native app there invites rename/merge breaks), and out of a separate GitHub repo
> (loses shared docs).

### 2.2 Runtime flow

```
                      ┌──────────────────────────────┐
  user taps icon  ──▶  │  bkemo app (SwiftUI)          │
                      │                               │
                      │  BiometricGate (Face ID)      │
                      │           │                   │
                      │           ▼                   │
                      │  RootView                     │
                      │   ├─ ComposerView (instant)   │
                      │   └─ RecentListView (lazy)    │
                      │                               │
                      │  SyncEngine (background)      │
                      │   ↑ SwiftData pending rows    │
                      └────────────┬──────────────────┘
                                   │ HTTPS + Bearer JWT
                                   ▼
                      https://bk.hax429.me/api/*
                         POST /api/auth/login            → {token}
                         POST /api/v1/note/upsert        → create note
                         POST /api/v1/note/list          → recent ~50
                         POST /api/v1/note/toggle-done   → complete todo
                         POST /api/v1/note/batch-trash    → soft-delete row
```

Composer and list are decoupled screens: the composer renders and focuses
**before** any network call. A cold launch in airplane mode never blocks the
composer. The list shows "You're offline" and falls back to whatever's in the
local store, optional cached snapshots of the last successful fetch — best-effort,
never a precondition for capture.

### 2.3 App Group storage

Three things live in the App Group container:

1. **SwiftData store** (`Memo.store`) — writeable by app, share extension, and
   widget (widget only reads).
2. **Keychain key** `bkemo.token` in a shared keychain access group — the JWT
   token. Share extension + widget will rarely need it (they write to SwiftData
   with `.pending` and let the app sync), but it's there for future read paths.
3. **Prefs** — last successful sync time, last used type (memo/todo), recent tags.

## 3. REST API contract (verified against the repo)

All endpoints live under `https://bk.hax429.me/api`. The iOS app is a pure REST
client; no tRPC, no NextAuth browser-flow. The token is a bearer JWT, refreshed by
re-login (no silent refresh in v1).

### 3.1 Auth

| Method | Path | Body | Response |
|---|---|---|---|
| `POST` | `/api/auth/login` | `{username, password}` | `{token, ...}` (or `{requiresTwoFactor, userId}`) |
| `POST` | `/api/auth/verify-2fa` | `{userId, twoFactorCode}` | `{token, ...}` |
| `POST` | `/api/auth/profile` | — (Bearer header) | `{user, token, expires}` (validate token) |

References: `app/src/components/Auth/auth-client.ts` `signIn('credentials', …)`,
`signIn('oauth-2fa', …)`, `getTokenData`.

### 3.2 Notes

| Method | Path | Body | Note |
|---|---|---|---|
| `POST` | `/api/v1/note/upsert` | `{content, type?, isImportant?, isUrgent?, dueDate?, parentNoteId?, attachments?, …}` | Create when no `id`; update when `id` set |
| `POST` | `/api/v1/note/list` | `{page, size, type?, isImportant?, isUrgent?, isCompleted?, orderBy?, …}` | Returns array with `id`, `content`, `type`, `isImportant`, `isUrgent`, `dueDate`, `completedAt`, `tags`, `attachments` |
| `POST` | `/api/v1/note/toggle-done` | `{id, done}` | Toggle completion |
| `POST` | `/api/v1/note/batch-trash` | `{ids:[…]}` | Soft-delete (trash) |
| `POST` | `/api/v1/note/batch-delete` | `{ids:[…]}` | Hard-delete |

Reference: `server/routerTrpc/note.ts:1035` (`upsert` mutation),
`scripts/demo-api.ts:68-101`, `scripts/test-api.ts:106-176`.

**Key contract details:**

- **`id` is server-assigned on create.** `upsert` accepts no client-generated ID;
  when `id` is omitted, the server creates a new `notes` row and returns the new
  `id`. The iOS app will use its own client UUID **only locally** for queue/sync
  tracking; it does not pass anything client-generated in the create payload.
- **Server extracts `#tags` from `content`** via `extractHashtags`
  (`server/routerTrpc/note.ts:20`). The app does **not** maintain a separate tags
  field; inline `#tag` tokens in the composer text are the single source of
  truth. `#important` and `#urgent` strings do *not* automatically map to the
  `isImportant` / `isUrgent` boolean columns; those must be sent explicitly as
  fields. See §6 for the composer's quick-toggle behavior.
- **`type` is `0=BLINKO, 1=NOTE, 2=TODO`** (`shared/lib/types.ts:14`). Default
  when omitted is `0` (BLINKO). The app sends `type: 0` for Memo and `type: 2`
  for Todo.
- **Scope**: `notes.upsert` is gated by the `notes:write` access-token scope if
  ever minted via scoped tokens (see `MCP.md`). The app uses session JWT from
  sign-in by default, so all `notes:*` are available — but `notes:write` is the
  exact scope a future read-only scenario would constrain.

### 3.3 Tags (optional read for quick-toggle)

| Method | Path | Body |
|---|---|---|
| `GET` | `/api/v1/tags/list` | — |

Used on first launch to fetch the user's tag tree for the PriorityToggle quick
chips (see §6). Cached in App Group prefs; refreshed at most once per 24 h.

## 4. Data model (SwiftData)

Single `@Model` entity lives in the App Group container:

```swift
import Foundation
import SwiftData

@Model
final class LocalMemo {
    /// Local UUID assigned at capture; never sent to server.
    @Attribute(.unique) var localId: UUID
    /// Server-assigned numeric id. nil while pending/error. Set on sync success.
    var serverId: Int?
    /// Raw stored content. Server parses #tags from this; app does too for UI only.
    var content: String
    /// 0=BLINKO (memo), 2=TODO. NoteType 1 (NOTE) is not used by the app.
    var type: Int
    /// Priority flags. Sent as fields on upsert.
    var isImportant: Bool
    var isUrgent: Bool
    var dueDate: Date?
    /// Original capture context. "" | "share" | "widget.memo" | "widget.todo".
    var source: String
    var createdAt: Date
    var updatedAt: Date
    var completedAt: Date?
    var syncState: String   // "pending" | "synced" | "error"
    /// Set when syncState == "error". Shown in red on the row.
    var syncError: String?
    /// If the user edited the row offline and we later enable offline edits
    /// (deferred). In v1 only `pending` + `synced` are used.
    var pendingEdit: Bool

    init(content: String, type: Int, source: String,
         isImportant: Bool = false, isUrgent: Bool = false,
         dueDate: Date? = nil) {
        self.localId = UUID()
        self.serverId = nil
        self.content = content
        self.type = type
        self.source = source
        self.isImportant = isImportant
        self.isUrgent = isUrgent
        self.dueDate = dueDate
        self.createdAt = .now
        self.updatedAt = .now
        self.syncState = "pending"
        self.pendingEdit = false
    }
}
```

**Container config (App Group shared):**

```swift
let schema = Schema([LocalMemo.self])
let config = ModelConfiguration(
    "Memo",
    schema: schema,
    url: appGroupURL.appendingPathComponent("Memo.store"),
    cloudKitDatabase: .none   // bkemo server is source of truth, not iCloud
)
let container = try ModelContainer(for: schema, configurations: config)
```

### Sync semantics

- On `app:online` event (combine `NWPathMonitor` `.satisfied` transition), and
  on app foreground after a network change, replay all `syncState == "pending"`
  rows oldest-first.
- For each row: `POST /api/v1/note/upsert` with `{content, type, isImportant,
  isUrgent, dueDate}` (no `id`). On `2xx`, store `serverId` from the response and
  set `syncState = "synced"`. On non-`2xx` (network timeout, 4xx except 401,
  5xx), set `syncState = "error"` and `syncError = "<message>"`; do **not**
  auto-retry forever.
- On `401`: signal `AuthManager.tokenExpired`; present the re-login sheet; leave
  the row in `pending` so the next fetch retry picks it up.
- **`createdAt` preservation**: send `createdAt` in the upsert body so server
  captures reflect the moment of capture, not the moment of sync.
- Edit/delete offline — **not in v1**. Only offline *create* is supported. Delete
  and edit are available only when online (the row is already synced; the call is
  fast and the queue stays one-flavored).

### List refresh policy

- On foreground, if online and more than 30 s since last sync, `POST
  /api/v1/note/list` with `{page: 1, size: 50, orderBy: "desc"}`.
- Merge the response with locally pending rows: pending rows always show first
  with a small "Pending" badge; synced rows appear after, in server order.
- The 30 s throttle prevents pathological foreground-loops from hammering the
  API.

## 5. UI / UX — composer-first layout

```
┌─────────────────────────────────────────────┐
│  [ Memo  | Todo ]        ⋯                 │   ← TypeToggle (segmented, default Memo)
├─────────────────────────────────────────────┤
│                                             │
│  <empty TextEditor, focused, multi-line>    │   ← ComposerView (TextEditor)
│                                             │
│  #important #urgent   ← only when TYPE=TODO│   ← PriorityToggle chips (small)
├─────────────────────────────────────────────┤
│  Recent                                     │   ← SectionHeader (mono, fg-3)
│  [○] Buy milk                  #home       │   ← MemoRow (todo shows check circle)
│  [○] Reply to Sam  ⚡           #work       │   ← ⚡ = urgent, ●=important
│  •  https://… cool article     source: share│   ← memo shows • and "source"
│  ⟳  pending: an hour ago…                  │   ← pending rows; ⟳ icon
│  ⚠  failed: bad token                       │   ← error rows; ⚠ icon, red
└─────────────────────────────────────────────┘
                          ↑ Save button floats above keyboard (chevron-up icon)
```

Behavior:

1. On launch the `RootView` appears after biometric unlock. The composer is the
   first responder: `TextEditor(text: $composerText)` with `.focused()` and
   `@FocusState` toggled true on appear.
2. The keyboard comes up automatically on fresh launch. **Phase 2 tweak**: keep
   keyboard auto-only on fresh launch, dismiss it if app returned from
   background — only if the user reports it's annoying (deferred, see §12).
3. `TypeToggle`: segmented control "Memo" / "Todo". Default Memo. Choice
   persists in App Group prefs across launches.
4. Saving:
   - Tap the floating Save button (chevron-up above the keyboard). The keyboard
     stays up, the field clears, focus stays, a "Saved" toast appears for ~1 s.
     Lets the user capture a burst of memos without a re-tap.
   - Return key = newline (multi-line native).
   - On Save: instantiate a `LocalMemo` with the current text + type + flags,
     insert into SwiftData with `syncState = "pending"`, clear the field, fire
     the SyncEngine to attempt immediate online upsert (this responds in <300 ms
     on a good connection; the row is already visible locally in the meantime).
5. Pending badge: rows with `syncState == "pending"` show a gray ⟳ with "Pending"
   text. On sync success the row slides to its real position in server order and
   the badge disappears.
6. Error badge: rows with `syncState == "error"` show a red ⚠ with `syncError`.
   Tap the row → a small "Retry" option in the detail sheet re-queues the row.

Recent list is capped at 50 server rows + all local pending rows. No pagination
in v1 (deferred until the user actually has >80 captures in recent memory).

### Detail sheet (tap a row)

- Plain `TextEditor` showing the raw content (no markdown rendering).
- Type toggle (Memo / Todo).
- Priority toggles if Todo.
- Save button updates the existing row; mutates `updatedAt`. Send `upsert` with
  `id = serverId` so the server updates instead of creating a new note. Works
  only online (offline edit is a non-goal).
- Delete button (red, with confirm) → `POST /api/v1/note/batch-trash` with the
  `serverId` → remove row from SwiftData.

### List row tap-vs-toggle (todos only)

- Tap the row → opens detail sheet.
- Tap the empty check circle on the left of a todo row → immediately calls
  `POST /api/v1/note/toggle-done` with `{id: serverId, done: true}` and marks
  `completedAt`. No sheet.
- Tap the filled check circle of a completed todo → toggles back to not-done.

Memos show a • bullet where the check circle appears on todos; tapping a memo
row opens the detail sheet (no quick action since memos have no completion).

## 6. Tags, priority, and the quick-toggle design

**Tags are inline `#tag` in the composer text.** The app does not manage a
separate tag list. The server parses them from `content` and creates `tag` rows
as needed (`server/routerTrpc/note.ts:1116-1146`).

`#important` and `#urgent` are **NOT** auto-mapped to the note's priority
columns. They must be sent as `isImportant: true` / `isUrgent: true` fields on
the upsert payload. The user confirmed a **quick-toggle for todos**:

- When `type == TODO`, a small row of two chips below the composer: `#important`
  (gold, `--important`) and `#urgent` (red, `--urgent`).
- Tapping a chip toggles a boolean; it does **not** insert `#important` text into
  the composer text (avoids the user accidentally typing a duplicate `#urgent` and
  making the chip ambiguous to parse).
- On Save: send `isImportant` / `isUrgent` as body fields, not embedded in
  `content`.
- When `type == Memo`: the priority chips are hidden.

Future quick-add chips (recent user tags as one-tap chips) are deferred — inline
typing is fast enough for v1 and new tags appear automatically on the server
after the first use. The chip list could later be sourced from `GET
/api/v1/tags/list`.

## 7. Voice input plan

The user explicitly flagged multilingual support + raw-audio-file saving as
future needs. To bound risk, voice is delivered in two phases:

### Phase A — v1: iOS system dictation (zero custom code)

Rely on the OS microphone key on the iOS software keyboard. On iOS 17+, neural
dictation is on-device, works offline, no permission prompt beyond what iOS
already shows, no extra code. The composer is a plain `TextEditor`, so the system
mic key works directly. The only affordance the app adds is a one-time hint line
under the keyboard: "Hold the 🎤 key to dictate" — dismissible, never shown again
after first tap.

This is sufficient for the 1-3 sentence quick-capture memos the app is built for.
It works with the system's multilingual setup (iOS dictation supports the user's
enabled keyboards automatically), so the multilingual requirement is satisfied to
some degree in v1 already.

### Phase B — v2: native speech framework + audio attachment

When V1 feels weak (long-form dictation, custom transcript UI, or when the user
wants the audio itself archived), ship:

1. **`SFSpeechRecognizer` streaming in-app**: a dedicated "Dictate…" sheet that
   requests the `NSSpeechRecognition` permission, streams partial transcripts in
   real time, returns the final transcript to the composer on Done. The Apple
   Speech framework supports per-request locale selection (`SFSpeechRecognizer(
   locale: Locale(identifier: "…"))`), so this is the **real multilingual
   surface** when the user wants to dictate in a language different from their
   keyboard.
2. **Audio attachment storage**: at the start of each request, write the mic
   stream to a local `.m4a` file in the App Group cache; on completion, upload
   the file to `POST /api/file/upload` (multipart — verify the server's file
   upload contract before starting Phase B; it is used by the web app, REST path
   documented in `app/src/lib/attachments.ts`). Then save the audio reference in a
   brand-new memo body via `note.upsert` with the `attachments` field populated —
   exactly the pattern in `scripts/test-api.ts:176`.

> **Action item for Phase B start**: confirm `/api/file/upload` max size, MIME
> whitelist, and returned path shape (`attachments.ts:7-37` hints at the shape).
> The v1 plan ships without that research.

This defers cleanly — Phase B is additive (a new sheet + an `AudioRecorder`
helper), not a rewrite of the composer. Phase A remains available as a fast
fallback.

> **Explicit cut from v1**: voice memo as a raw audio file (i.e., Voice Memos
> style "record 30 s, send the m4a"). Voice *input* is in scope; audio-file
> *attachment* is a Phase B concern.

## 8. Auth model

- First launch: a small sign-in sheet (`username`, `password`, "Sign in").
  Hardcoded server endpoint `https://bk.hax429.me`; no URL prompt. Hide the sheet
  behind normal first-run flow; biometric gate runs **after** sign-in, never
  before the token is acquired.
- On submit: `POST /api/auth/login`. If the response is a 2FA challenge
  (`requiresTwoFactor`), show a code field, submit via
  `/api/auth/verify-2fa`. Store the final `token` (JWT) in Keychain under the
  shared keychain access group.
- Biometric: on every foreground (cold or warm), `LAContext.evaluatePolicy(
  .deviceOwnerAuthenticationWithBiometrics)`. On success: reveal RootView. On
  failure: stay on a "bkemo locked" screen with a "Try again" button. Biometric
  adds <100 ms; well within the "instant capture" budget. A Settings toggle lets
  the user turn biometric lock off if it interferes with the speed expectation.
- 401 handling: any REST call that returns `401` causes `AuthManager` to clear
  the Keychain token and present the sign-in sheet again, with a toast "Your
  session expired".
- Token refresh: **none in v1**. JWT expiry = re-login. If server-side refresh
  ever lands, this becomes a silent refresh.

No scoped-access-token paste path in v1. The MCP server uses scoped tokens; the
phone app is too small to need either UX. Revisit only if the user wants to
avoid typing their password on the phone.

## 9. Offline sync design (verified)

What offline operations does the app support?

| Operation | Offline? | Notes |
|---|---|---|
| Create memo / todo | ✅ Yes | Insert `LocalMemo` with `syncState="pending"`; SyncEngine replays on reconnect |
| Mark todo done | ❌ No | Requires `serverId`; offline rows have none yet. The user shouldn't be completing things they just captured, and a queue for one operation is not worth it for v1 |
| Edit text | ❌ No | Detail sheet Edit is disabled for offline rows; the user can long-press → delete the pending row and re-capture instead |
| Delete row | ⚠️ Only pending | Pending rows can be deleted locally without a server call. Synced rows: needs network → disable the button offline |

### Sync trigger

```swift
// app/App/SyncMonitor.swift
class SyncMonitor: ObservableObject {
    private let monitor = NWPathMonitor()
    @Published var isOnline = false

    init() {
        monitor.pathUpdateHandler = { [weak self] path in
            Task { @MainActor in
                self?.isOnline = (path.status == .satisfied)
                if path.status == .satisfied {
                    await SyncEngine.shared.replayPending()
                    await SyncEngine.shared.refreshRecentList(force: false)
                }
            }
        }
        monitor.start(queue: .main)
    }
}
```

Combined with `scenePhase` observation: foreground → try sync if last sync >30 s
ago; network change → sync; explicit pull-to-refresh on the list → force sync.

### Sync replay pseudocode

```swift
// app/Data/SyncEngine.swift
func replayPending() async {
    let pending = try? fetch(FetchDescriptor<LocalMemo>(
        predicate: #Predicate { $0.syncState == "pending" },
        sortBy: [SortDescriptor(\.createdAt, order: .forward)]))
    guard let pending else { return }
    for memo in pending {
        do {
            let payload: [String: Any] = [
                "content": memo.content,
                "type": memo.type,
                "isImportant": memo.isImportant,
                "isUrgent": memo.isUrgent,
                "createdAt": ISO8601DateFormatter().string(from: memo.createdAt)
            ]
            if let due = memo.dueDate { payload["dueDate"] = ISO8601DateFormatter().string(from: due) }
            let resp = try await client.post("/api/v1/note/upsert", body: payload)
            memo.serverId = resp.id
            memo.syncState = "synced"
            try container.mainContext.save()
        } catch let e as APIError where e.code == 401 {
            // signal AuthManager; do not advance
            return
        } catch {
            memo.syncState = "error"
            memo.syncError = String(describing: error)
            try container.mainContext.save()
        }
    }
}
```

### Share extension offline behavior

Share extensions cannot reliably trigger background sync. They write their row
to the App Group SwiftData with `syncState="pending"` and show "Saved to bkemo";
SyncEngine only actually syncs when the main app next foregrounds. This matches
the user's expectation: the capture happened; the sync waits for a real app
launch. The recent-list row appears immediately (pending) when the user next
opens the app.

## 10. iOS Widget

WidgetKit, iOS 17+. Interactive widgets enabled (we can use `Button` with an
`AppIntent`).

### v1 sizes

- **Small**: two stacked buttons "Memo" and "Todo". Each button runs an
  `AppIntent` that opens the main app with `?type=0` or `?type=2` set on a URL
  or via `openAppWhenRun: true` + an `AppEntity`/shared-deep-link identifier. The
  app's `.onOpenURL` or `.onContinueUserActivity` parses it and pre-sets the
  TypeToggle before focusing the keyboard.
- **Medium**: same two buttons side-by-side, plus a one-line preview of the most
  recent capture ("Last memo: Buy milk · 2 min ago"). The preview reads the App
  Group SwiftData at timeline-refresh time. Timeline refresh: every 15 min
  (`TimelineReloadPolicy.after(Date().addingTimeInterval(900))`); widgets cannot
  be updated more frequently than the system allows.

### Cuts (deferred)

- **Lock Screen round widget**: deferred — adds a third timeline for marginal
  value.
- **Large widget**: deferred.
- **Inline-create from widget** (skip the composer, create an empty memo and
  background-sync it): deferred. The user has confirmed empty-memos would
  generate garbage.

### Passing the type into the app

Use `AppIntent.openAppWhenRun = true` and store the choice in App Group prefs
(`group.me.hax429.bk` `UserDefaults` key `pendingType`), then
`Environment(\.openURL)` with a deep-link URL `bkemo://open?type=2`. The app's
`WindowGroup.onOpenURL` reads `pendingType`, sets the composer's `TypeToggle`
selection, clears the pref. Composer still focuses the keyboard as normal.

## 11. Share Extension

Bundle id `me.hax429.bk.ShareExtension` (or `me.hax429.bk.share`), part of the
same Xcode project so it shares code with the app target via a Swift package or
shared-source-file membership.

Behavior, step by step:

1. User taps Share in Safari / YouTube / a chat app.
2. The share sheet shows **"bkemo"** as one of the options.
3. User taps it → a **pre-save sheet** appears (SwiftUI host of a
   `UIViewControllerRepresentable` wrapping `SLComposeServiceViewController` is
   overkill; a custom sheet is simpler and more on-brand). The sheet contains:
   - A `TextEditor` with the prefilled content, **auto-focused** (parity with the
     main app).
   - A `TypeToggle` (default Memo).
   - `PriorityToggle` chips if type=Todo.
   - A `Save` button top-right.
4. Content prefill logic:
   - If the host app passed a **URL**: fire `LPMetadataProvider` (async, with a
     2 s timeout). On success: prefilled content is
     `"<fetched page title>\n\n<URL>"`. On timeout or failure: prefill with just
     the URL string.
   - If the host app passed **text** (a chat message, a tweet, a selected quote):
     prefill with the text directly.
   - If the host app passed an **image** (v1 cut): ignore silently; do not
     prefill.
5. On Save: insert a `LocalMemo` with `syncState="pending"` and `source="share"`
   into the App Group SwiftData. Show "Saved to bkemo" toast. Dismiss the sheet.
   Sync happens when the main app next foregrounds.

### Future media support (planned, deferred from v1)

When the user wants photo/file sharing, the path is:

1. Extract the image / file from `NSExtensionContext` attachments via
   `NSItemProvider.loadItem(forTypeIdentifier: …)`.
2. Write to a temporary file in the App Group's `Caches`.
3. Since the share extension can't reliably make a long-running network call,
   follow the same strategy as text captures in v1: write a pending row with
   `source="share"`, store the file path + name + size + MIME as fields on the
   `LocalMemo` (extend the `@Model` with `pendingAttachmentPath`,
   `pendingAttachmentName`, `pendingAttachmentType`, `pendingAttachmentSize`).
4. When the main app foregrounds, `SyncEngine` uploads each pending attachment to
   `/api/file/upload`, then calls `/api/v1/note/upsert` with the attachment
   metadata (the shape in `scripts/test-api.ts:176`), then marks the row
   `synced`.

This keeps v1 single-text-flavored and makes the attachment path an additive
Phase B with no rewrite.

> **Action item before Phase B share media**: confirm the `/api/file/upload`
> multipart contract (field names, OAuth Bearer requirement, size cap, MIME
> allowlist) and the `attachments[]` shape the server expects in
> `note.upsert`. Read `app/src/lib/attachments.ts` and the file router
> (`server/routerTrpc/file.ts`) before implementation.
