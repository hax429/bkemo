# Integration foundation plan

**Status:** proposed

**Priority:** P0

**Goal:** one authorization and synchronization module for every external
adapter

## Problem

bkemo already exposes REST, access tokens, change cursors, SSE notifications,
Markdown transfer, and MCP. These capabilities are valuable but currently live
at several seams. Adding Obsidian or more connectors directly on top of routes
would duplicate ownership checks, token handling, retries, and conflict rules.

The foundation should deepen this cluster: callers learn a small interface,
while bkemo keeps complex policy inside one module.

## Proposed module

Create `server/out/`:

```text
server/out/
  gateway.ts            external interface
  actor.ts              verified identity + capability construction
  operations.ts         curated query/command union
  changes.ts            portable change batches
  concurrency.ts        revisions and conditional writes
  idempotency.ts        replay-safe mutation keys
  audit.ts              redacted integration events
  adapters/
    rest.ts
    mcp.ts
```

The gateway owns:

- account ownership and token-scope enforcement;
- portable-ID lookup and internal numeric-ID resolution;
- input limits and normalized errors;
- conditional writes and conflict results;
- idempotency-key storage and replay;
- audit records without secrets or note bodies;
- data-shape translation that is common across adapters.

REST and MCP become adapters at this seam. Obsidian adds the second real
document-sync adapter. Prisma, `userCaller`, and raw external tokens remain
inside the implementation.

## Contract additions

### Portable documents

Define a stable `IntegrationDocument` derived from current note fields:

```ts
type IntegrationDocument = {
  portableId: string;
  revision: string;
  type: 'memo' | 'note' | 'todo';
  content: string;
  createdAt: string;
  updatedAt: string;
  dueDate: string | null;
  completedAt: string | null;
  important: boolean;
  urgent: boolean;
  archived: boolean;
  recycled: boolean;
  tags: Array<{ portableId: string; name: string }>;
  attachments: Array<{
    portableId: string;
    name: string;
    mediaType: string;
    size: string;
    downloadPath: string;
  }>;
  parentPortableId: string | null;
  referencePortableIds: string[];
};
```

`revision` must be generated by the server. Do not use caller-supplied
`updatedAt` as a concurrency token. A hash of the canonical mutable state or a
monotonic note revision are both acceptable; a monotonic revision is easier to
reason about.

### Conditional commands

All external writes use:

```ts
type IntegrationCommand = {
  idempotencyKey: string;
  portableId?: string;
  expectedRevision?: string;
  operation: 'create' | 'update' | 'complete' | 'archive' | 'trash' | 'restore';
  patch: unknown;
};
```

Results distinguish:

- `applied`;
- `replayed` (same idempotency key and payload);
- `conflict` (current revision returned, no write);
- `forbidden`;
- `invalid`.

Hard delete is not in the general integration interface. It may remain a
separately privileged administrative operation.

### Change batches

Extend the existing `noteChange` cursor contract rather than adding another
polling table:

- return portable IDs in removals and snapshots;
- include the current document revision;
- keep changes ordered by the append-only cursor;
- support bounded pages and deterministic resume;
- retain tombstones long enough for dormant clients, or provide an explicit
  full-resync signal when the requested cursor is too old.

SSE remains a wake-up signal. The cursor endpoint is authoritative.

## Security model

- Build `IntegrationActor` only from a verified session or revocable access
  token.
- Carry concrete scopes through every internal call.
- Never create a synthetic `superadmin` caller for an integration request.
- Separate read, write, attachment, sharing, automation, and destructive
  capabilities.
- Rate-limit by account, credential, operation, and source.
- Redact authorization headers, environment variables, note content, provider
  secrets, and tool arguments from routine logs.
- Bound text sizes, batch sizes, attachment sizes, and execution time.
- Reject outbound private-network URLs unless an administrator explicitly
  enables a narrowly defined allowlist.

## Phases

### F0 — contract tests

- Capture current access-token and note-change behavior in focused tests.
- Add negative tests for cross-account reads, revoked tokens, insufficient
  scope, replay, and stale revisions.
- Define the integration document and command schemas.

### F1 — actor and gateway

- Implement actor construction from the existing request context.
- Route portable-ID reads and curated note mutations through the gateway.
- Add redacted audit events and idempotency persistence.
- Keep existing REST behavior compatible while new endpoints opt into the
  gateway.

### F2 — concurrency and changes

- Add server-controlled note revisions.
- Add conditional updates and portable tombstones.
- Extend `notes.changes` with revisioned portable documents.
- Test disconnect, pagination, duplicate delivery, and full resync.

### F3 — adapter migration

- Migrate MCP tools to the gateway.
- Use the same interface for the Obsidian plugin endpoints.
- Remove duplicate adapter-level ownership and mutation logic after parity
  tests pass.

## Verification

- Unit tests at the `IntegrationGateway` interface.
- PostgreSQL integration tests for revisions, idempotency, and ordered changes.
- OpenAPI contract test for every public integration operation.
- A replay test that runs the same change log continuously and after simulated
  disconnect, then compares final state.
- Security tests proving every scope denial and cross-account denial.

## Exit criteria

- MCP and Obsidian can use the same gateway without provider-specific privilege
  shortcuts.
- Duplicate requests do not duplicate notes or comments.
- Conflicting writes never silently overwrite data.
- All externally visible identifiers can survive import/export and database
  restore.
